# 提示词的设计

## 原始目标与课堂要求
用户要求实际实现、运行、验证并交付任务管理应用，六项核心要求是 CRUD、三种状态、三档优先级、拖拽看板、深色记忆与本地持久化。课程需要仓库链接、提示词设计、每项功能截图。

## 结构与设计理由
| 结构 | 作用 |
| --- | --- |
| 角色 | 明确 Agent 对实现、验证、交付共同负责 |
| 目标与上下文 | 说明软件工程课堂及可追溯证据要求 |
| 范围 | Vue/Vite/Tailwind/localStorage；排除后端、登录、AI 聊天等 |
| 功能规格 | F01—F09 拆解为用户可观察的行为 |
| 验收 | 列出正常、无效、取消、刷新、空列、异常存储等路径 |
| 流程 | 每轮目标→修改→真实浏览器验证→Git 提交 |
| 交付 | 规定截图命名、索引、文档和 GitHub 核验 |
| 停止条件 | 全部完成才宣称全部交付；阻塞必须明确区分本地与远程 |

设计理由：用可观察行为降低歧义；通过分轮测试和提交防止事后虚构开发过程；用功能—测试—截图映射形成证据链；明确排除无关功能控制规模；规定损坏存储保护避免为了“看似正常”破坏数据；GitHub 可见性要求确认，避免未经授权公开。

## 提示来源与真实迭代
- 用户真实发送：一条完整任务书，全文逐字保存于下文及 original-prompt.md。内容从本任务会话的用户消息提取，不包含系统提示、账户凭据或无关对话。
- 本任务书预先规定：五轮任务是同一条用户提示内的阶段要求，并非五条后续用户消息。
- Agent 自主计划：建立 outputs/taskflow；选用原生 dialog 和 HTML 拖放；用独立 Playwright Chrome 上下文进行验收；存储成功后才提交状态；使用单次 safe.directory 适应沙箱账户差异。这些是实现决策，不是用户发来的指令。
- 后续用户修改/反馈：截至本地最终验收，没有收到后续功能修改提示或评价。网络权限批准属于环境授权，不伪装成需求迭代。
- 每轮对应实现、命令、失败与修复详见 development-log.md；截图与验收对应关系见 acceptance.md。

## 用户实际发送的提示词全文

以下完整保留原任务书（包括其中的转义和 HTML 字符表示）：

---
你是一名负责实现、验证和交付的前端开发 Agent。请按照以下任务书，实际完成一个可运行的任务管理 Web 应用，并整理课程作业需要的全部交付材料。

不要只提供方案、代码片段或静态页面。你需要在工作目录中创建项目、运行应用、验证功能、记录开发过程、生成真实截图，并完成权限允许范围内的 GitHub 仓库交付。

一、任务背景与最终目标

这是软件工程课程的一次 Agentic 开发实践。

课堂实践明确要求：
1\. 任务增删改查：标题必填，描述选填。
2\. 三种任务状态：待办、进行中、完成。
3\. 三档优先级：高为红色、中为黄色、低为绿色。
4\. 看板视图：三列卡片，拖拽即可修改任务状态。
5\. 深色模式：一键切换，并记住用户选择。
6\. 浏览器数据持久化：刷新页面后任务数据不丢失。

课程推荐技术栈：
\- Vue 3
\- Vite
\- Tailwind CSS
\- localStorage

课堂要求按轮次开发，每轮遵循：
明确本轮目标 → 执行开发 → 浏览器验证 → Git commit → 进入下一轮。

课程群要求提交：
1\. GitHub 仓库链接。
2\. 提示词的设计。
3\. 每一个功能实际运行的截图。

因此，最终成果既要包含能用的应用，也要包含可追溯的开发过程和验收证据。

二、范围与默认技术决策

1\. 使用 Vue 3、Vite、Tailwind CSS 和 localStorage，实现纯前端应用。
2\. 优先使用 Vue 3 Composition API 与 \<script setup>。
3\. 默认使用 JavaScript；若现有项目已使用 TypeScript，则沿用，不为切换语言重建项目。
4\. 页面、按钮、提示信息和提交文档使用简体中文。
5\. 不增加登录注册、后端接口、云数据库、团队协作、AI 聊天、支付等无关功能。
6\. 优先用简单、可靠的方式完成课堂要求，避免不必要的依赖和复杂架构。
7\. 根据实际安装的依赖版本使用对应配置，提交包管理器锁文件。
8\. 允许在本项目内创建文件、安装必要项目依赖、启动服务、执行测试及进行本地 Git 提交；遵循运行环境的权限限制。
9\. 开始前检查当前目录、现有文件、项目规范和 Git 状态，保护用户已有改动。不要覆盖无关文件，不要修改全局 Git 身份或进行强制推送。
10\. 非阻塞的实现细节由你采用合理默认值并记录，不必逐项询问。只有缺少关键权限、目标仓库不明确或存在覆盖风险时才请求必要信息。

本应用中的“Agentic”指使用 Agent 完成开发的方式，不要求在应用内接入大模型。

三、功能规格与验收要求

F01：创建任务

\- 提供明显的“新建任务”入口。
\- 表单包含标题、描述、状态、优先级。
\- 标题必填，去除首尾空白后不能为空。
\- 描述选填，留空也可以创建任务。
\- 状态默认“待办”，优先级默认“中”。
\- 提交成功后关闭表单或重置表单，立即更新页面。
\- 无效输入显示清晰的中文提示，不创建任务。
\- 防止一次提交因重复点击而产生重复任务。

验收：
\- 只填标题可以创建任务。
\- 空标题和纯空格标题均被阻止。
\- 新任务的状态、优先级与表单一致。

F02：查看任务

\- 提供基础任务列表，以及可切换的看板视图。
\- 两个视图共享同一份任务数据，不各自维护不同副本。
\- 展示任务标题、状态、优先级。
\- 能查看完整描述；长文本可以在卡片上截断，但应有查看完整内容的入口。
\- 无任务时显示友好的空状态和新建入口。
\- 长标题和长描述不能撑破布局。

验收：
\- 新增后能在列表和看板中找到同一条任务。
\- 能查看完整的任务信息。
\- 空数据状态下页面仍然可正常操作。

F03：编辑任务

\- 可修改标题、描述、状态、优先级。
\- 编辑表单回填原值。
\- 保存后立即更新所有相关视图。
\- 标题沿用创建时的校验规则。
\- 取消编辑不修改原数据。
\- 编辑既有任务时保持任务 ID 不变。

验收：
\- 修改后的字段正确显示并持久化。
\- 修改状态后任务出现在对应看板列。
\- 取消修改后原信息不变。

F04：删除任务

\- 每条任务提供删除入口。
\- 删除前进行确认，明确显示将删除的任务。
\- 取消删除时保留任务。
\- 确认删除后，列表、看板和存储数据同步更新。
\- 不误删其他任务。

验收：
\- 取消删除不影响数据。
\- 确认删除后任务消失，刷新也不会重新出现。

F05：三种状态

\- 固定为“待办”“进行中”“完成”。
\- 内部使用稳定枚举，例如 todo、in\_progress、done。
\- 支持通过编辑表单或状态控件修改状态。
\- 任意状态之间都可以切换。
\- 列表和看板展示保持一致。

验收：
\- 三种状态均可创建、显示和切换。
\- 状态修改不会重置任务标题、描述或优先级。

F06：三档优先级

\- 高：红色。
\- 中：黄色。
\- 低：绿色。
\- 用文字标签配合颜色，不只依赖颜色表达含义。
\- 浅色和深色模式下均应清晰可读。

验收：
\- 同时展示高、中、低三档任务，颜色与文字对应正确。
\- 修改优先级后即时更新，刷新后保持。

F07：三列看板与拖拽

\- 三列依次为“待办”“进行中”“完成”。
\- 任务以卡片形式出现在对应列。
\- 支持把卡片拖到其他列，松开后更新任务状态。
\- 支持拖入空列。
\- 拖拽时提供可辨认的拖动或落点反馈。
\- 同列拖动或取消拖动不能误改状态。
\- 跨列移动只改变状态，不丢失任务、不复制任务。
\- 保存状态变化，刷新后任务仍位于正确列。
\- 无法方便拖拽的场景仍可通过状态控件完成状态修改。
\- 不要求实现同列排序。

验收：
\- 实际完成至少一次“待办 → 进行中”、一次“进行中 → 完成”及一次反向移动。
\- 至少验证一次拖入空列。
\- 拖拽后任务总数保持不变，状态持久化成功。
\- 必须验证真实拖拽交互，不能仅通过直接改数据或下拉框改状态代替拖拽验收。

F08：深色模式

\- 页面提供一键切换浅色／深色模式的按钮。
\- 背景、卡片、文本、表单、弹窗和边框统一适配。
\- 使用 localStorage 保存用户选择。
\- 刷新后恢复上次选择。
\- 首次访问可以采用浅色模式；不强制增加跟随系统功能。

验收：
\- 浅色与深色可双向切换。
\- 深色模式下刷新后仍然保持深色。
\- 表单和优先级标签在两种模式下都可读。

F09：本地持久化

\- 使用 localStorage 保存任务。
\- 创建、编辑、删除和拖拽修改状态后均同步保存。
\- 初始化时恢复已有数据。
\- 为任务和主题使用明确的存储键名。
\- 对 JSON 解析失败、数据结构异常和写入失败做基本处理，避免应用白屏。
\- 存储失败时给出可理解的提示，不显示虚假的保存成功信息。
\- 空任务数组是合法状态，删除全部任务后刷新不能自动恢复演示任务。
\- 不因读取失败而静默清空用户原始存储。

验收：
\- 新增、编辑、删除、改状态后分别刷新，结果保持一致。
\- 关闭页面再打开同一应用地址，任务和主题仍可恢复。
\- 异常存储不会导致整个页面不可使用。

四、数据与界面设计

建议使用统一数据模型：

Task:
\- id：唯一且稳定的字符串
\- title：非空字符串
\- description：字符串，允许为空
\- status：todo | in\_progress | done
\- priority：high | medium | low
\- createdAt：创建时间
\- updatedAt：更新时间

要求：
1\. 列表和看板从同一份任务状态派生。
2\. 状态、优先级的内部值与中文显示标签集中映射。
3\. 任务逻辑、存储逻辑与界面组件适当分离，不把全部逻辑塞进一个巨型组件。
4\. 用户输入按普通文本展示，避免直接当 HTML 渲染。
5\. 可采用以下模块划分，但允许根据实际情况简化：
&#x20;  \- 应用入口与页面布局
&#x20;  \- 任务表单
&#x20;  \- 任务列表与任务卡片
&#x20;  \- 看板与看板列
&#x20;  \- 任务状态管理
&#x20;  \- localStorage 读写
&#x20;  \- 主题管理
6\. 界面整洁，按钮含义明确，具备清楚的空状态、错误提示和操作反馈。
7\. 桌面端清晰显示三列看板；窄屏可横向滚动或采用合理布局，不能使功能无法使用。
8\. 演示任务通过正常应用操作或独立的演示数据准备流程创建，不要每次启动都注入数据。

五、按轮次完成开发

不要一次性生成全部代码后补写虚假的开发历史。请真实执行以下轮次，每轮完成验证与提交，再进入下一轮。

每轮开始时简要说明：
\- 本轮目标。
\- 计划修改的模块。
\- 验收方法。

每轮结束时记录：
\- 实际完成的内容。
\- 执行的命令和结果。
\- 浏览器验证操作及结果。
\- 实际遇到的问题和修复。
\- Git commit hash。
\- 尚未解决的问题。

只需要简洁的决策依据和操作记录，不需要输出内部思维过程。

第 1 轮：项目骨架

\- 检查环境，创建或完善 Vue 3 + Vite + Tailwind CSS 项目。
\- 建立基础目录结构和页面布局。
\- 验证开发服务能启动，浏览器能打开，样式正常加载。
\- 进行一次本地 Git 提交。

第 2 轮：核心任务管理

\- 实现创建、查看、编辑、删除。
\- 实现标题校验、三种状态和三档优先级。
\- 验证正常路径、无效输入、取消编辑和取消删除。
\- 验证通过后提交。

第 3 轮：数据持久化

\- 实现任务保存与恢复。
\- 验证增删改及状态修改后刷新不丢失。
\- 验证空数组和异常存储处理。
\- 验证通过后提交。

第 4 轮：看板与交互

\- 实现三列看板、视图切换与跨列拖拽。
\- 验证拖入空列、反向拖动、总数不变及刷新恢复。
\- 验证通过后提交。

第 5 轮：深色模式与最终交付

\- 实现主题切换和记忆。
\- 检查响应式、长文本和空状态。
\- 执行最终回归与生产构建。
\- 截取全部功能证据，整理文档并提交。
\- 最后处理 GitHub 推送与仓库链接验证。

课堂参考时间是开发 20—25 分钟、报告 5—10 分钟。优先完成必做功能，不因美化或扩展功能拖延核心交付。若实际超时，真实记录完成范围与剩余工作，不得通过省略验证或伪造记录声称完成。

六、验证要求

1\. 使用实际浏览器验证用户操作；构建成功不能代替功能验收。
2\. 对标题校验、任务更新与存储恢复等关键逻辑编写适量自动化测试。
3\. 有浏览器自动化工具时，可编写覆盖核心流程的端到端测试。
4\. 使用稳定的页面定位方式，避免脆弱的固定延时。
5\. 至少执行依赖安装、项目配置的测试命令及生产构建命令。
6\. 如果项目配置了 lint 或类型检查，也要执行；未配置的检查应明确说明，不得声称通过。
7\. 检查实际浏览器控制台是否存在应用错误，修复影响功能的问题。
8\. 失败时依据报错和可复现步骤修复，再重新验证受影响的功能。
9\. 保留真实测试结果，明确区分“已验证”“失败”“未验证”。

九、Git 与 GitHub 交付

1\. 在项目范围内使用 Git 管理代码，每轮验证后形成有意义的提交。
2\. 提交代码、配置、锁文件、必要测试和提交文档。
3\. 不提交 node\_modules、密钥、账户凭据及无关缓存。
4\. Git 身份缺失时请求用户提供或配置，不自行编造姓名邮箱。
5\. 检查已有远程仓库和 GitHub 登录状态。
6\. 用户已指定目标仓库并授权推送时，按该授权完成推送。
7\. 需要新建 GitHub 仓库时，先完成本地项目及验证，再确认必要的账户、仓库名称和可见性；不得擅自把代码公开。
8\. 若没有 GitHub 权限或尚未登录，完成其余工作，给出准确的后续命令与所需信息，标注“远程仓库交付待完成”。
9\. 不创建占位仓库链接，不把本地路径当成 GitHub 链接。
10\. 推送成功后核验远程地址、分支和提交，提供真实、可访问且便于教师查看的仓库链接。
11\. 不要求额外部署网站或创建 PR；除非用户另行要求，不扩展为部署任务。
